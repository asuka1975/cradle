# 思想

## 仕様はハーネスである

エージェントに機能要件を伝えるのは人間で、そこがボトルネックになる。人間の中にしかない要件を、人間が正しく伝えられないからだ。
一方、非機能要件はほとんど一般論であり、エージェントが極めて得意な領域である。

だから仕様を**エージェントを縛るハーネス**として書く。仕様が決定論的なら、エージェントの仕事は「仕様どおりに作る」に縮み、得意な非機能要件に集中できる。

## 決定論的であるとは

- 仕様の問いに**推測で答えない**。モデルを動かして、その出力を引用する（`spec-query`）。
- 仕様を変えたとき、**変えるつもりのなかったことが変わっていない**ことを機械で確かめる（`golden-check`）。
- 仕様から生成されたものを**手で直さない**（hook が止める）。直すなら源を直して再生成し、影響範囲を機械で出す（`regen-impact`）。
- 規約は**検査できる形**にする。文章で守らせる規則は、機械で検査する規則より弱い。

Lean で書かれた仕様がこれを満たすのは、型検査と証明検査が無矛盾性を保証し、`#guard` と golden が挙動を固定し、CLI として実行できるからだ。

## 人間が最後に確かめる

モデルの正しさは、人間が画面を通して動かしたときに初めて分かる。だから画面の相手は最初は Lean（モデルそのもの）で、バックエンドは最後に作る。
確認で修正点が出たら戻る先は Lean の 1 か所だけ。下流を先に触らない。

## 決まっていないことは実装しない

型にしようとして初めて露呈する曖昧さが、探索の最大の副産物。それは問い（MQ）として人間に戻し、モデルはゆるい解釈のまま進む。
「未決なので〜している」と書ける欄を無くすと、決まっていないことを実装したうえで通すことができなくなる。

## 正本は 1 か所

同じ情報を 2 か所に写せば、片方は必ず腐る。ドメインの事実は documents、決定は設計文書、契約は openapi、挙動は Lean。
コードは documents を ID で指し返さない（Lean だけが出典として持てる）。ステータス語はコードに書かない。経緯は規約に混ぜない。
