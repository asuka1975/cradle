# コードコメントの規約

- **ステータスをコードに書かない**: open / resolved / 反映済 / 却下 / 未決 / 検証済。可変の状態を 2 か所に持てば、更新されない側（コード）が必ず古くなり、根拠の顔をして残る。
- **ドメインの事実の ID をコードに書かない**: HS-xxx / UX-xxx / MQ-xxx / INFRA-x-xxx / イベント#n。撤回された ID を引いたコメントは読者を撤回済みの記述へ案内する。
  **例外は Lean モデルだけ**（形式化の出典として ID を持てる。ステータス語は不可。`cradle unslop` が実在と撤回を検査する）。
- **経緯・日付・事故談を書かない**: 「〜に撤回」「旧 xxx」「以前は」。経緯は documents（ddd / ai-notes）の持ち物。コードには**いまの形の理由**だけを書く。
- **書いてよいもの**: その関数・型が何をするか、なぜこの書き方か（性能・方言・言語仕様の都合など、コードから読み取れない事情）、呼び出し側が守るべき前提。
- **書かないもの**: ドメインの事実そのもの（正本は documents と lean）、宣言名をなぞるだけのコメント、逃げ言葉（たぶん・とりあえず・一旦・should work）、
  理由の無い TODO（`TODO(理由):` の形にする。Lean の未証明は `sorry` + `-- TODO(proof):`）、装飾の絵文字。
- **モデルとの対応は契約テストで取る。** 散文で「モデルどおり」と主張しない — 散文は検査できない。
- 実装がモデルの決定を再導出しそうになったら（並び順・可否・遷移先）、コメントで正当化せず、その判断を Lean の View / validate に足す。
