# バックエンド設計品質

## 認証・認可

- 認可は deny-by-default。`permitAll` はヘルスチェックだけ。立場（ロール）で門を分けるパスは 1 か所で定義する。
- トークンは iss / aud / 期限 / 用途（`token_use`）を明示検証する。ステートレス。CORS は backend に持たない（same-origin は前段が保つ）。
- 名義（`ActorContext`）を組み立ててよいのは認証アダプタ 1 か所だけ。Controller も UseCase も DI で受け取る。リクエスト本文・クエリから名義を作らない（lint で縛る）。
- 名義の種別（本人 / 使い始め / 管理の印）は認証層で分け、エンドポイントがどれを要求するかを決める。Controller に名義検査を書かない。
- 立場はトークンに入れない（モデル上の事実として DB で決まる）。
- 「本人が主体になれない」拒否は経路で割れないよう 1 つの語彙に揃える（401 / 403 / 404 の意味を混ぜない）。
- 検証を飛ばすプロファイルを作らない。local も本番と同じ経路（JWT + JWKS）を通し、違うのは発行者の URL だけ。

## 外部サービス連携（IdP・DB・時計・その他）

- 外部呼び出し（JWKS 取得など）にはタイムアウト・キャッシュ・失敗時の挙動を明示する。ライブラリ既定に任せない。
- 外部障害を利用者の誤り（401 / 400）に化けさせない。障害は 503 / 500 として区別し、アラームが鳴る経路に載せる。
- 外部との接点はポート（interface）で切り、実装は `infrastructure/` に置く。ドメインに外部の語彙を持ち込まない。
- 外部能力の Port の要求・観測の語彙は Lean（`Application/Port/`）が正で、interface と型は生成される。Adapter は外部のあらゆる応答（欠落・未知のコード・不正データ・通信失敗・タイムアウト）を `Outcome` の構成子に写し、「答えない」を「いない」や業務の拒否に丸めない。副作用が成立した可能性のあるタイムアウトを「実行されなかった」と断定しない。
- 冪等性・再試行は業務の観測を変えない範囲で。再試行で二重実行が起きる操作は再試行しない。

## ログ設計

- 構造化ログ（JSON）にする。相関 ID（リクエスト ID）を全ログに載せ、レスポンスヘッダにも返す。
- コマンド（更新系 execute）の監査ログを 1 行残す: 誰が（名義の同一性）・何を（UseCase 名）・宛先・結果（ok / 失敗語彙）。破壊的操作（無効化・取り消し）は必須。
- PII・トークン・本文の全文をログに書かない。500 は内部の例外をログに残し、本文には写さない。
- ログレベル: 業務の拒否（422 / 403）は INFO、境界の形の誤り（400）は WARN 以下、内部起因は ERROR。

## 設定

- 既定値で黙って開発設定に倒れない。プロファイル無指定は安全に失敗する（`spring.profiles.default` を dev にしない）。
- 秘密は環境変数か秘密管理から。設定ファイル・state・ログに載せない。`application-test.yml` は `src/test/resources/` に置く。
- 認証設定（発行者・audience）は妥当性検証を持ち、空文字や平文 http を受け入れない。
- 入力の長さ上限を契約（openapi）に書き、DB 列幅超過を 500 にしない。

## 観測

- ヘルスチェック・5xx 率・応答時間・稼働数のアラームを持ち、通知先を空にしない。
